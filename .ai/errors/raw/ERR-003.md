### ERR-003: C6 复位后 strap=0 恒进 Joint Download 模式（wait usb download），app 无法启动

- **症状**: hello_world 烧录成功（hash verified，0x10000 镜像头 0xE9 有效），eFuse 正常，但经 USB-Serial/JTAG 软件复位后打印 `rst:0x15 (USB_UART_HPSYS),boot:0x0 (USB_BOOT) wait usb download`，strap=0x00000000（GPIO8=0,GPIO9=0 → Joint Download 模式）
- **排查史**: 软件复位序列穷举（ClassicReset/USBJTAGSerialReset/HardReset/纯RTS/DTR矩阵/双线组合 ×7+）全部一致进下载模式；eFuse 全部正常；镜像有效
- **根因（用户手动 RST 后修正）**: 不是硬件 strap 问题——**是 usbipd + USB-Serial/JTAG 虚拟复位的时序问题**：软件复位（DTR/RTS 触发的 USB_UART_HPSYS 复位）经 usbipd 虚拟链路传播时，strap 采样时刻 boot 线电平不对 → 进下载模式；**硬件 RST 按键复位不走这条路径** → 正常 boot。strap=0 是 USB 复位传播时序的果，不是 BOOT 键卡死的果
- **修复**: 烧录/复位后需要 app 启动时，**按板上 RST 键**（硬��复位）；脚本自动化验证不可靠，监控流程改为"烧录完成 → 提示手动 RST → 静默监听串口"
- **规律提炼**: usbipd 虚拟 USB-Serial/JTAG 的 DTR/RTS 复位不可信（strap 采样时序被虚拟化破坏），硬件 RST 按键是可靠路径；esptool 烧录本身不受影响（下载模式正是软件复位能进入的）
- **二次提炼接口**: META 规则 —— [BUILD] WSL+usbipd+C6 环境：烧录后验证 app 启动一律手动 RST 键，不要依赖 esptool --after hard-reset；监控用 pyserial 静默监听（open 时 DTR/RTS 保持 False 也会触发一次复位，等这次复位过完再读）

- **复现次数**: 1

### ERR-009: 设备在 sector 落盘路径硬挂死——BLE 链路掉线、串口静默、不再广播（固件侧已修复：notify_sem 泄漏）

- **症状**: 上位机修复 ERR-008 后真机传输推进到 sector 2-3 即失败，四次复现（run1 @ sector2 尾包、run3 @ sector3 尾包、固件排查日 runA/runB 均 @ sector3 尾包 write-with-response `Unreachable`，说明连接在此之前已死）。掉线后设备：BLE 不再广播（>40s，非正常重启的 3-5s 窗口）、串口完全静默（DTR 已断言仍无输出）、无 panic/寄存器转储打印、WDT 未触发复位；USB 枚举仍在（esptool 可连）。只能 esptool `--after hard_reset chip_id` 硬复位恢复，复位后广播正常。
- **主机侧证据**: `/tmp/flash3.log`（run3 完整输出：3 个 sector ACK 全部接受，sector 3 body 包 8 个 write-with-response 全部成功，尾包失败）；run1 输出（sector 2 尾包失败）；runA/runB 输出与 run3 模式一致（sector 1/2/3 ACK 全收，sector 3 尾包死）。
- **设备侧证据**（WSL /dev/ttyACM0 同步抓取，DTR 断言）: runB 抓取（/tmp/panic2.log，修复前固件）：连接 conn_itvl=6、MTU=517；`recv ota start cmd, fw_length=656720`（20637ms）→ Start ACK(att=22) → sector0 ACK(att=16, 20937ms) → `progress saved: sector=1, offset=4096`（20947ms）→ sector1 ACK（21247ms）→ sector2 ACK（21577ms）→ **此后日志彻底静默**；host 侧仍成功写入 sector 3 的 8 个 body 包（NimBLE host 任务还在收包但不打印），尾包时链路已死。
- **根因**（三问闭环，静态+动态双重证实）:
  1. 为什么 ota_task 停止落盘？→ `notify_sem` 为计数信号量（max 100, 初值 0，创建后 give 一次 → count=1）。ota_task 主循环每处理一个 ringbuf item 就 `xSemaphoreTake(notify_sem)` 一次，但 **esp_ota_write 成功的正常迭代路径不 give**（example 循环体末尾有无条件 `xSemaphoreGive(notify_sem)`，移植时丢失）。于是 count 在 sector 0 写完后归 0；ota_task 收到 sector 1 数据后在 take 上**永久阻塞**（日志仅剩 `progress saved: sector=1` 后静默，与 4 次复现吻合）。组件侧 notify_sem 的 take 仅存在于 Stop 命令处理器（nimble_ota.c:556 / ble_ota.c:705，META-001 隐式契约），正常 sector ACK 路径不经过它。
  2. 为什么 host 侧死在"尾包 Unreachable"而不是更早？→ ota_task 停止消费后 ringbuf（8192B）每 sector 塞入 ~4096B：sector 1/2 的 push 恰好还有空间（被 ota_task 收走未归还的 item 恰好腾出对称空间），ACK 正常发出（日志 att_handle=16 两次）；到下一 sector 尾包时 ringbuf 已满，NimBLE host 任务在 GATT 写回调内的 `xRingbufferSend(s_ringbuf, …, portMAX_DELAY)` **永久阻塞**——该 ATT write-with-response 永远得不到应答，上位机超时报 `Unreachable`。"8 个 body 包成功 + 尾包失败"与"死于 sector 2 或 3 取决于 ota_task 与 host 的竞速"完全由 4096×2=8192 的缓冲几何决定。
  3. 为什么无 panic、无 WDT 复位、不广播？→ 全链是**任务级死等**而非崩溃：ota_task 阻塞在 take、host 任务阻塞在 ringbuf send（均 portMAX_DELAY，TWDT 默认不订阅这两个任务且 CONFIG_ESP_TASK_WDT_PANIC 未开）；断连事件永远到不了已冻死的 host 任务 → GAP DISCONNECT 处理器（内含重新广播）不执行 → 不广播；串口自然静默。仅硬复位可恢复。
- **修复**（embedded-firmware-engineer 2026-09-02，firmware/main/ota_task.c）:
  1. 恢复 example 语义：主循环体末尾**无条件** `xSemaphoreGive(notify_sem)`（正常迭代路径与 item_size==0 路径统一收口）；
  2. esp_ota_write 失败路径顺序修正为"还 ringbuf item → give → goto OTA_ERROR"，保证异常退出时不持信号量；
  3. `recv_len >= fw_len` 完成路径保持显式 give 后 break（此后循环不再运行，不会造成 count 累积——互斥用法下 count 恒在 0/1 之间）。
  构建零错误（bin 0xA0550=656,720B），已烧录；**真机全链路回归 PASS**（2026-09-02：161 sectors / 656,720B / 45.9s（14 KB/s），esp_restart 后 3-5s 重新广播，OTA SUCCESS，packets=1443 jumps=0 reconnects=0 tail_retries=0；修复前同一路径 4/4 死于 sector 2-3）。
- **上位机已做的配套硬化**: 连接掉线时主动 cancel 并回收挂起 ACK waiter 的异常，消除 `Task exception was never retrieved` 噪音（send_start/send_stop/send_sector 三处）。
- **规律提炼**: 从 example 移植"信号量包裹临界段"的循环体时，take/give 配对必须覆盖**所有**路径（正常迭代、continue、break、goto），任何一条正常路径漏 give 都会让信号量 count 单调泄漏，最终冻结整条生产者-消费者流水线——且阻塞点分散在两个任务（消费任务阻塞在自体 take，生产任务随后阻塞在队满 send），症状表现为"设备静默挂死、死在尾包"而非本任务崩溃。审查方法：对循环内每个 take，从循环入口到出口逐路径核对 give 的到达性；特别警惕"成功路径看起来不需要 give"的直觉（本例 give 不在 if 内而在循环末尾，移植时被当作可选）。
- **二次提炼接口**: 已提炼 META-006-CONCURRENCY（example 的 take/give 配对是组件回路的隐式协议，移植丢失任一侧都会冻结流水线对端）。

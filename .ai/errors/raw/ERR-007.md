### ERR-007: ota_task 启动时缓存 fw_len 恒为 0——首个 sector 落盘即触发 esp_ota_end（代码审查发现，未上机复现）

- **症状**: 代码审查发现（尚未真机触发）：firmware/main/ota_task.c:65 `const uint32_t fw_len = esp_ble_ota_get_fw_length();` 在任务启动时一次性读取。真机一旦开始传数据，第一个 sector 回调（4096B）落盘后 `recv_len(4096) >= fw_len(0)` 恒成立 → 立即 break → esp_ota_end 对一个只写了 4KB 的镜像大概率报错（镜像长度校验失败）→ OTA_ERROR 分支，BLE 传输卡死
- **根因**: 官方 example（ble_ota_example/main/app_main.c:395）在 for 循环条件里**每次实时调用** `esp_ble_ota_get_fw_length()`；移植改造时改成了任务开头缓存。而 ota_task（优先级 5）由 app_main 末段创建，与 app_main 同优先级但先进入阻塞读 ringbuf，让出 CPU；Start 命令（设置 fw_length 的唯一时机）必然发生在 ota_task 启动**之后**——缓存值永远是被 Start 命令更新前的 0。这是"读取时机"与"写入时机"的跨任务顺序错误
- **修复**: （待固件侧执行）ota_task.c 恢复 example 语义：循环条件改为 `recv_len >= esp_ble_ota_get_fw_length()` 实时读取；或显式等待 Start 完成（fw_length > 0 且 start_ota 置位）后再进入数据循环
- **规律提炼**: 移植官方 example 时，"性能优化式"的缓存提取（把函数调用提为局部 const）可能改变跨任务时序语义。对"由外部命令填充、任务循环消费"的量，消费端要么实时读，要么同步等待其有效；缓存的前提是存在 happens-before 边
- **二次提炼接口**: META 规则 —— [CONCURRENCY] 跨任务共享的"命令注入型"参数（对端命令写入、本地任务读取），消费任务禁止启动时缓存，必须实时读取或等就绪信号；移植 example 时凡是移动了读取位置的 diff 都要问"原位置是否本身是时序屏障"
- **首次出现**: 2026-09-01
- **复现次数**: 1（静态发现，dry-run 未触发——握手不含数据）

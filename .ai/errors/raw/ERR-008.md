### ERR-008: 上位机把 sector 0 的全零成功 ACK 误判为坏帧并重发，导致传输中止

- **症状**: 真实 .bin 传输时 sector 0 写入成功（设备日志 `progress saved: sector=1, offset=4096`，att_handle=16 回成功 indication），但上位机打印 `[W] sector ACK bad frame: 0000000000000000000000000000000000000000`（整帧 20 字节全零），随后重发 sector 0 → 设备拒绝（`sector index error, cur: 1, recv: 0`，GATT Unlikely Error）→ 循环耗尽 max_jumps 传输中止。
- **根因**（三问）:
  1. 为什么全零帧被判坏帧？→ `send_sector` 里用 `frame[0:2] != ACK_HEADER(0x0003)` 判帧头。
  2. 为什么这里不该有帧头检查？→ RECV_FW 的 sector ACK **没有固定头**：nimble_ota.c:390-399 成功路径 `cmd_ack[0:2]=回显收到的 sector`、`[2:4]=0x0000`、`[4:18]` 保持零初始化、`[18:20]=CRC16(前 18B)`。`0x0003` 头只存在于 COMMAND ACK（nimble_ota.c:187 零初始化为 0x03,0x00,...）。 sector=0 且成功时前 18 字节全零，而 `CRC16-XMODEM(18×0x00)=0x0000`，整帧 20 字节全零是完全自洽的合法成功 ACK。
  3. 为什么当初会写错？→ 把 COMMAND ACK 的帧格式（有 0x0003 头）错误泛化到了 RECV_FW ACK；模块 docstring 也写成了统一有头，错误认知沉淀进了文档。
- **修复**: host/ble_ota_host.py `send_sector` 帧校验改为「长度==20 + 尾部 CRC16 自校验」，删除 0x0003 头检查；CRC 不匹配 → 拒绝重发（保留）；status=0x0000 → 成功（以我们发送的 sector_index 为准，echo 不符仅 vlog 提示）；status=0x0002 → frame[4:6]=cur_sector 期望值跳转（读位核对 nimble_ota.c:206-207 无误，frame[0:2] 是回显收到值而非期望值）。同步修正模块 docstring 的帧格式描述。
- **验证**: 协议单测 PASS（全零帧过 CRC / sector N 成功帧重建解析 / 错误 ACK 字段位置 / 破坏帧拒绝）；真机回归 sector 0/1/2 ACK 全部被接受（进度推进到 sector 3/161，此前 sector 0 即卡死）——ERR-008 本身已修复。
- **规律提炼**: 帧合法性判定只能依赖**自校验字段**（CRC、长度、magic 与载荷的绑定关系），禁止用"非零检查""与载荷无关的固定头"等外观判定；存在全零/全 0xFF 合法帧的协议里，"看起来像坏帧"的帧必须先过 CRC 再下结论。同类风险点：全 0xFF 尾包 sector 标志（nimble_ota.c:197 "Last sector"）同样会被外观判定误杀。
- **二次提炼接口**: 见 META-005-DATA_INTEGRITY。
